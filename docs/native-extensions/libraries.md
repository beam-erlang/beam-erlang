# Passive BEAM libraries

A passive library describes ordinary BEAM modules and resident NIF registrations.
It creates no VM, runs no Erlang startup and does not invoke a NIF initializer
when opened. Mapping native code can execute platform constructors. Native code
and descriptors are trusted inputs.

The format in `<beam/library.h>` is experimental and tied to an exact SDK build.
The descriptor includes its size, format version, SDK build identity, diagnostic
name, module byte spans with origins, and typed resident NIF registrations. It
contains no dependency discovery or startup hooks. A shared image exports the
constant data symbol `beam_library_descriptor_v1`; static libraries expose unique
accessors generated by the SDK helper.

## Authoring

Use an explicitly selected installed SDK. Compile Erlang sources with its
`BEAM::CLI`, then supply the resulting paths to the library helper:

```cmake
find_package(BEAM CONFIG REQUIRED COMPONENTS Runtime Host CLI NIF)
add_library(example_native STATIC example_nif.c)
beam_target_nif(example_native MODULE example)
add_library(example_library STATIC)
beam_target_library(example_library NAME example
    MODULES example
    BEAM_FILES "${CMAKE_CURRENT_BINARY_DIR}/example.beam"
    NIF_TARGETS example_native)
```

`MODULES` and `BEAM_FILES` correspond one for one. `NIF_TARGETS` is optional;
bytecode-only libraries use the same format. Each native target must have a
unique module name and matching SDK identity. The helper embeds the bytes and
records the resident accessor without calling it. Python 3.9 or later is required
on the authoring host.

The target properties `BEAM_LIBRARY_HEADER` and `BEAM_LIBRARY_ACCESSOR` identify
the generated declaration and unique accessor. Calling that accessor retains the
descriptor and its referenced native objects in a static link. Static targets
do not select a runtime: the final host links `BEAM::Runtime` or
`BEAM::RuntimeStatic`. A shared native library must select suitable platform
linkage explicitly; a dependency on another runtime image is rejected by native
admission.

## Acquisition and composition

Link `BEAM::Host` and include `<beam/library.h>`. Open a shared library with an
absolute path using `beam_library_open`, or pass a resident descriptor to
`beam_library_from_static`. Inspect copied metadata with
`beam_library_get_inputs`. Its byte spans and owner record are borrowed until
the library is released.

An explicit module origin is preserved as a copied label. With a null origin,
acquisition uses the canonical image path plus `#module` for shared delivery,
or the descriptor name plus `#module` for static delivery. Generated descriptors
use this default, so relocating a shared library preserves accurate provenance.

Supply the inputs through composition's `modules`, `builtin_nifs` and
`native_owners` fields. Combine inventories explicitly when selecting several
libraries; preparation rejects module and native-registration conflicts. The
library layer validates descriptors and identities. Composition and VM loading
perform bytecode validation.

Successful preparation retains the owner independently. The caller may then
release its library reference. A VM retains its preparation, so the caller may
also release the preparation after VM initialization. Native code remains
resident until native resources, unload callbacks and registries have been
reclaimed. A static descriptor, its bytecode and native code must remain resident
for every reference; linked executable storage satisfies this contract.

Resident table accessors run during VM initialization. The owning Erlang module
later calls ordinary `erlang:load_nif/2`, supplying its actual load information.
Opening a library or supplying its modules does not start its services. The host
chooses startup calls independently of the descriptor.

## Explicit bindings and generic image admission

Explicit bindings are a different route from resident registrations. A
`beam_nif_binding` declares a module and either a normalized resident accessor or
a platform initializer. Preparation copies the declaration without calling the
initializer. After starting the VM, call `beam_vm_bind_nif` for that module.
The platform form preserves Windows callback-table injection.

Successful binding is idempotent and supplies `undefined` as load information.
Invalid selections or missing modules do not start native initialization.
Failure after initialization begins stops the VM; inspect its report and
terminate it before creating a fresh VM. Ordinary reload/rebinding is rejected.

`<beam/native_image.h>` provides generic mapping, symbol lookup, canonical path
inspection and an owner record. It uses the ordinary native loader's runtime
image checks and interprets no library descriptor. Paths and dependency-search
inputs must remain unchanged while used. Matching SDK text does not replace
runtime image admission.

## Returning hosts

Returning orchestration is in the optional static `BEAM::Host` target. Include
`<beam/boot.h>` for `beam_return_*` and copied outcomes; `<beam/beam.h>` exposes
only VM interfaces. Runtime-only consumers require neither Host nor its headers,
archive, library authoring helper or ordinary startup assets.

## Support inventories

The optional SDK verifier exposes separate `startup`, `host`, `output` and `code`
inventories, each containing its corresponding `beam_` module. Startup needs only
`beam_startup`; output and code acquisition use `beam_host` plus the selected
policy module and ordinary base operations they invoke. The aggregate `services`
inventory is a convenience selection above the VM. Supplying any inventory runs
nothing and grants no native permission.
